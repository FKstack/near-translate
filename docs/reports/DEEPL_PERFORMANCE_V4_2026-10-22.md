# DeepL 第32次429追查、连接加速与第四轮实测

2026-10-22，继续以沉浸式翻译和 OJBetter 的实际产物为对照。结论是：**已排除“固定第32次必然限流”，接入了可选连接准备，两个新前台标签的首段正文降到1.468 / 1.378秒；全文14.749 / 14.931秒，尚未达到10秒。** 初始可见4段全部完成为2.599 / 1.904秒，不能宣称完整首屏已经稳定低于2秒。

成功、失败、控制实验与每包数字时序均保存在[第四轮证据](../evidence/deepl-speed-v4-go-2026-10-22.json)。没有将短句、部分成功、缓存重译或点击前等待包装成全文成绩。

## 1. 第32次究竟是什么问题

### 可直接验证的事实

旧8路/100ms与8路/200ms都在序号32收到HTTP429；当时该包为5项、1,471字符，前32包累计230项、46,508字符。后台最多8个在途，**32是累计请求序号，既不是32个同时连接，也不是数组项数上限触发**。成功窗口轮也能处理相同序号和相同项数/字符数的包。

本轮通过实际用户Edge中同一个扩展ID、同一匿名provider与原生网络完成控制实验：

| 控制 | 请求/文本项/字符 | 结果 | 能说明什么 |
| --- | --- | --- | --- |
| 重建的第32包候选作为首包 | 1 / 5 / 1,471 | 1次200、5项有效输出 | 候选内容不是一发就拒绝；旧日志缺逐包正文哈希，不能声称逐字节重放了原始第32包 |
| 不同公开短句 | 32 / 32 / 1,060 | 32次200 | 请求序号到32本身不充分 |
| 保留旧前32包的每包项数序列，改为不同公开短片段 | 32 / 230 / 5,542 | 32次200、230项有效输出 | 请求数及累计项数本身不充分；字符量、语言工作量等仍不同 |
| 10路全文候选，无启动窗口 | 第20包返回429；共发出20包 | 10次200、1次429、9次取消 | 不是固定32规则，整轮不合格 |
| 已准备连接的9路全文候选，无启动窗口 | 第20包返回429；收到拒绝前已发出24包 | 15次200、1次429、8次取消 | 消除首次握手仍不能让此负载通过，整轮不合格 |
| 恢复8路及30次/12秒本地窗口 | 每轮38 / 251 / 53,505 | 两轮均38次200 | 当前有完整成功证据的策略 |

两轮新的429都通过增强后的安全诊断得到`responseReason: rate-limit`，没有提取到具体quota/concurrency类别、整数错误码、Retry-After或已支持格式的RateLimit数字。**这是上游通用频控拒绝，不是浏览器本地连接池报错；但上游没有给出可据此还原精确阈值的反馈。** 不能把字段未提取到扩大为“响应没有任何其他字段”。

低字符控制、较高并发失败和放缓累计启动后成功，更符合“工作量与实际到达时序共同影响限流”的解释，但这仍是推断。并发、每段语义、累计字符、服务负载和窗口状态没有被完全分离，不能宣布已查明“每秒多少字符”或“多少秒固定多少次”。取消也不能撤回服务端已经收到的文字。

所有429均立即暂停队列、取消同服务在途并持久保存冷却，没有自动重试、更换身份、IP、连接来重置配额，或清空冷却。恢复后的完整复测是在自然等待后、运行时确认剩余冷却为0才启动。

## 2. 竞品的真实实现没有提供匿名大包捷径

OJBetter当前默认分支AtCoder文件仍与固定提交`860106c63ef7bb7d4ec5dcd709f80a9f9a6f1a46`一致，1.25.1，blob为`1565e6f4d37c533a6f563bb1db5a733adf052aeb`。其匿名DeepL走旧`www2.deepl.com/jsonrpc`，一次一个raw/UI区块，自动源语言、alternatives=3，串行完成后再等200ms。没有发现第32请求特殊分支；此前原版TM整篇Go内容单raw实测为413，不能从小样本成功推断能快速完成全文。[固定实现](https://github.com/beijixiaohu/OJBetter/blob/860106c63ef7bb7d4ec5dcd709f80a9f9a6f1a46/script/release/atcoder-better.user.js#L15911)

实际取得的沉浸式商店1.34.2与固定仓库1.34.3分别核验。可比较的匿名`d`路线是默认关闭的Canary适配器，旧RPC、默认3项/800字符、1050ms启动预约；普通DeepL入口对应Pro/custom Key。默认动态翻译首屏的体验也不能当作53,505字符已经全部完成。[固定匿名实现](https://github.com/immersive-translate/immersive-translate/blob/609114bcb337ecb968498bc1b917d55679f39e24/dist/userscript/immersive-translate.user.js#L6269)

发布产物用`reverse-engineer-anything`技能做惰性静态核验，并用AST独立定位；REA图有时间上限和覆盖裁剪，没有将图中缺失当作功能不存在的证明。版本、哈希、请求映射、重试及限制详见[沉浸式产物审计](../evidence/immersive-v4-implementation.md)与[协议复核](../evidence/deepl-v4-protocol-research.md)。没有照搬竞品的官方Origin伪装或429通用重试。

## 3. 减少请求次数的边界

近译仍遵守所核验官方匿名客户端的**一次逻辑输入合计1,500个UTF-16单元**。官方`Fk`先合计所有`sourceTexts.length`，再进入后续分组；不是数组每项各有1,500。5,000属于登录免费状态。**这证明官方客户端预算，不是本轮实测了服务端1501硬边界**；已有OneShot真实样本均未超1,500，旧RPC大包200和mock单测不能作为新端点大包支持的证据。[官方预算调用链](../evidence/deepl-anonymous-budget-v3-2026-10-22.md)

53,505字符至少需要36包；保留137字符首包时至少37包。离线已有达到下界的构造，当前38包只多一包。普通空白压缩节省为零：源文本已经规范化，没有连续、首尾或其他空白。即便保留字母间词边界后删除其余所有空格，也仅减少2.03%，而且未证明语义安全，远不足以把全文压成30或32包。

OJBetter的数字段落标记可以做失败拒绝映射，但不是OneShot承诺保留的结构协议，标记还占预算。仅靠换行数量一致不能证明没有合段/拆段抵消。本轮不删除正文、破坏词边界或以不可靠映射换取更少请求。[离线包形状与空白审计](../evidence/deepl-v4-limit-analysis.md)

`source_lang=en`属于正常可选字段，但已有235字符小样本不足以排除满批次收益，也未显示明显可靠提升。其中auto约8秒的样本含约6.76秒TLS，不能将它归因为自动检测。本轮没有把英文写死到通用翻译协议，也没有引入未经证实的匿名低延迟模型参数。

## 4. 新发现并实际接入的连接准备

本机首次TLS握手常占约0.85–1.9秒。此前内容页preconnect及扩展来源iframe未观察到被SW复用；HEAD401、缺标准协商字段的OPTIONS405也没有作为生产路径。

本轮补齐`Access-Control-Request-Method: POST`与`Access-Control-Request-Headers: authorization,content-type`后，同一固定地址对扩展原生自身Origin返回204。第一轮因自设严格网页CORS门禁而0POST；响应缺CORS许可头，不代表已获host权限的扩展SW被Chrome禁止跨源。Chrome明确区分普通页面/content script与有主机权限的扩展SW。[Chrome官方网络权限说明](https://developer.chrome.com/docs/extensions/develop/concepts/network-requests)

随后独立资格只发1次OPTIONS和1次公开POST：204后POST200，均使用同一HTTP/2 connection132，POST没有新握手。准备2.606秒、POST1.996秒、导航到结果6.709秒全部记录。这是手工HTTP连接准备，**不宣称网页CORS准入、浏览器预检缓存或DeepL保证的预热接口**；缺CORS字段也没有通过改响应、Origin或浏览器安全开关来伪造许可。

### R2架构与设计细节

- `platform/deepl-web-transport`唯一持有权限、DNR规则和数字指标。新规则74002仅匹配自身initiator、精确OneShot地址、OPTIONS、xhr，只增加上述两个标准协商头；POST、Origin、User-Agent和响应不修改。无Cookie、API Key、正文、Referrer或自定义页面地址。缺权限或规则安装失败时普通POST仍可用。
- `DeepLWebProvider.prepareNetwork()`通过注入的`prepareTransport`执行，复用已有`RequestScheduler`槽位、启动预算、429诊断及冷却。它不产生翻译事件，普通翻译不等待准备。重复准备共享一个owner；5秒期限包含排队。取消后owner和执行槽等待真正的transport/响应清理结束再释放，迟到响应不开始新任务。
- `platform/deepl-web-state`独立持有trusted session键`deepl-web:prepare-at:v1`，至少30秒才可预留下一次**准备调度尝试**，跨worker重启保留，取消/失败不退款；存储失败仅跳过准备。此时间不承诺实际HTTP发包间隔，因为预留后还可能排队；它也不是上游官方额度。TTL拒绝不占共享启动预算。
- 新runtime内容脚本只在DeepL开启、网页/服务host权限和可选DNR权限均具备时注册为顶层`document_start`。可见HTTP(S)非PDF页面才发送无正文/URL的准备消息。后台再次核验browser提供的sender、tab/document/requestId、设置与权限；旧文档取消不能取消新owner。离开页面、停用、切换或撤权会取消对应/服务准备。
- 设置页用现有可选DNR权限作为能力开关，可点击“启用连接加速（可选）”或“关闭连接加速”。历史已有该权限时显示为启用。**启用后可能在没有点击翻译时先联系DeepL，但正文只在点击后发送。** 没有新增必需权限、依赖包或模型设置schema；原模型配置与Key保留。
- OPTIONS另记`preparationCount/activePreparations/preparations`，最多64条，不混入正文POST计数。ResourceTiming没有method，相近匹配窗口歧义时省略，避免把准备TLS误算到POST。测速从建标签前保存导航基线，点击前若出现正文POST就拒绝冷翻译成绩；额外/失败准备、迟到请求同样不能通过优化验收。

完整资格原始哈希和生命周期说明见[网络准备设计](../evidence/deepl-v4-network-preparation-design.md)。

## 6. 验证、部署与未达目标

713/713单测、26/26 Edge整页定向回归通过；最终响应清理修正另重跑准备/停止/429三个受影响Edge路径，3/3通过。类型、模块依赖边界、Chrome/Edge构建通过。模拟测试没有被当作真实网络性能。

最终页面另做独立只读DOM核验：251原文、251译文、唯一翻译栏，28个pre与176个code内部均0译文；5个无汉字输出为BBC Worldwide、Canonical、Heroku、SoundCloud及go.dev。核验本身没有发起翻译或申请权限，数字及原始哈希已收入第四轮证据。

最终实际安装程序与恢复后的Edge构建哈希一致，包含新`content-scripts/network-prepare.js`；[部署证据](../evidence/deepl-speed-v4-deployment-2026-10-22.json)。未读取、导出或改动用户Key/Cookie，未重新打包旧ZIP。先前授权的临时webRequest诊断已撤销；新能力使用的是设置页可关闭的可选DNR权限，并明确披露其元数据请求用途。

本轮交付的是**通过两次完整真实测试的连接准备能力和更充分的429证据**。全文10秒仍未达，完整首屏2秒也只有一轮达到。当前没有证明一个在匿名、完整范围、严格映射且无扩展译文缓存条件下，能安全稳定满足全文10秒的新服务能力；这不等于证明未来协议或所有网络下永远不可能。精确上游流控维度仍未知，不以继续盲升并发或放宽预算冒充已修复根因。
