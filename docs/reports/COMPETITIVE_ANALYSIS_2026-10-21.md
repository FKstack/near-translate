# 近译 0.7.0 竞品分析与改进建议

主对标已按用户要求聚焦沉浸式翻译：请优先阅读[近译 × 沉浸式翻译专项对标](IMMERSIVE_TRANSLATE_COMPARISON_2026-10-21.md)。本文件保留多竞品背景；后续优先级以专项报告为准。

最新产品约束：近译保持免费，不建设本产品收费服务。免 API Key 路线的最新证据与设计见[登录态可行性分析](NO_API_SESSION_TRANSLATION_FEASIBILITY_2026-10-21.md)。竞品收费信息仅作为对比，不作为近译收费计划。

调研日期：2026-10-21（Asia/Singapore）。本报告结合本地源码、项目验证记录，以及竞品官方文档、版本说明。三个子代理均按要求使用 GPT-6.1-Sol / xhigh，分别研究成熟产品、开源 BYOK 产品和本地产品体验。

**核心判断：面向大众通用翻译，近译当前最明显的差距是依赖用户自行配置 API、固定英译简中、日常网页操作与适配不够完善，以及文档等常见场景覆盖不足。首要目标应是装好即可得到可靠译文，并在高频场景中保持简单、一致的体验。**

用户已确认定位：**面向大众的通用翻译工具**。本报告据此调整为通用路线；技术精读、术语与长难句拆解作为增强能力。普通用户不应必须了解服务商、API Key、模型名或协议才能开始使用。首发可继续集中桌面 Chrome/Edge，但应覆盖普通用户读网页、查词句、写外语和读文档的核心需求。

**1. 证据范围与判断边界**

- 本地依据为当前 0.7.0 的 README、src、tests、构建配置与 docs。本文的“未发现”限定在这些范围，不代表项目之外没有方案或实验分支。
- 竞品能力以公开官方资料为依据，不等同于本次实际安装体验，也不代表所有功能免费、所有版本均已上线。
- 未进行同条件翻译质量、速度、成本和可用性横评，因而不对产品打主观总分，不宣称我们更快或更准。
- 本次未调用用户的真实 API、未产生翻译计费请求；项目已有实测记录均明确标为历史证据。
- 动态价格页未能可靠确认的金额不列入报告；付费门槛按功能和方案说明描述。

KISS 的版本边界需要特别注意：本次对比以 v2.1.1 正式版文档为主，其 PDF/图片文档翻译和本地边缘 AI 仍在未来规划中。默认开发分支已经介绍的功能，不全部算作正式版现有能力。[v2.1.1 文档](https://github.com/fishjar/kiss-translator/blob/v2.1.1/README.md)

首次使用和收费也要分开比较。沉浸式有基础免费能力与高级服务，免费请求存在公平使用限制；Trancy 的免费权益包含基础翻译和自定义引擎，付费扩展学习与文档额度；Read Frog 无账号也可使用自有 provider，云端笔记、复习和内置 AI 另有条件。近译的自带 Key 路线并非天然最便宜，应把 API 费用和配置时间共同计入用户成本。[沉浸式方案](https://immersivetranslate.com/en/pricing/)、[Trancy 权益](https://www.trancy.org/pricing)、[Read Frog 方案](https://www.readfrog.app/en/docs/account-and-plans)

**4. 面向大众的主要差距与优先级**

这里的 P0 指下一轮产品迭代优先项，不表示安全漏洞或线上事故。影响与工作量是规划判断，尚未做开发估时。

| 优先级 | 差距 | 对用户的影响 | 建议改进 | 相对工作量 |
| --- | --- | --- | --- | --- |
| P0 | 依赖开发者安装与自备 API Key，保存不等于连接成功 | 大众用户在首个译文前就可能退出 | 商店分发、无需自备 Key 的默认服务、最少设置、故障引导；BYOK 留作高级选项 | 中至高，含持续服务成本 |
| P0 | 固定英译简中，缺少语言选择与自动识别 | 日语、韩语等页面及反向翻译不能形成完整体验 | 自动识别、可选源/目标语言、记住偏好，逐语言验收 | 中至高 |
| P0 | 缺少当前页快捷入口、站点偏好和阅读模式选择 | 高频操作繁琐，坏页面无法自助处理 | 工具栏/右键/快捷键翻译、正文优先、双语/仅译文、本站规则 | 中至高 |
| P0 | 真实质量证据不足，固定高并发、用量反馈缺失 | 可用性和成本难以预期 | 通用多语言质量集、服务级并发与有限退避、清楚的额度与失败状态 | 中，需持续维护 |
| P1 | 输入框翻译尚未形成产品路径 | 能阅读但不能方便地回复、发帖和写外语 | 选中文字或输入框翻译、替换前预览、撤销和语言切换 | 中 |
| P1 | PDF 仅划词，缺少按页/全文翻译 | 文档阅读需要反复选区 | 先支持文字 PDF 按页与全文双语阅读，再评估导出和扫描件 | 中至高 |
| P1/P2 | 图片/截图与视频字幕未覆盖 | 图片文字和视频内容需要换工具 | 以图片翻译、已有字幕双语为候选，按真实任务需求排序；无字幕转写后置 | 较高 |
| P2 | 缺少术语表与明确的篇章上下文机制 | 专业或长文内容一致性不足 | 个人术语、保留词、可选上下文增强 | 中至较高 |
| P2 | 缺少收藏与复习 | 进阶学习用户难积累词句 | 先显式收藏、来源与导出，再考虑复习；不作为大众首用前置条件 | 中 |
| P2 | 仅桌面 Chrome/Edge | 其他平台用户无法使用 | 根据需求扩展 Firefox/Safari/移动端，保持核心体验一致 | 较高 |

**4.1 首次体验：当前最大的转化风险**

现有文档需要构建或解压加载、填写服务/地址/模型/Key、授权 API 域名、启用网页权限，再刷新页面。设置页已有步骤分区和服务预设，这是好的基础；问题是仍把协议和配置细节集中交给用户处理。[安装说明](../guides/INSTALL.md)、[设置页](../../src/entrypoints/options/main.tsx#L75)

代码里的保存逻辑做字段校验、域名授权和配置保存，没有实际翻译连通检测；弹窗的“已就绪”来自 Key/开关/权限状态，因此不能证明模型可访问。[保存逻辑](../../src/entrypoints/options/main.tsx#L48)、[就绪提示](../../src/entrypoints/popup/main.tsx#L27)

大众默认路径应是：商店安装 → 选择目标语言或接受默认值 → 打开网页点击翻译。默认页面不要求输入 Key、选择模型或理解 JSON。自带 Key、本地模型和自定义网关放到高级设置，并继续提供用户主动触发的连接检测，区分鉴权、模型权限、格式不支持、限流和网络失败；“已保存”和“已验证”分开表达。

需要首先确定可持续的默认服务方案，优先核验服务商官方账号授权或本地翻译能力。面向大众不能只把 Key 输入框藏起来，也不能把公共密钥打包进扩展。普通模式显示服务状态、上游可用额度和额度耗尽后的处理；BYOK 模式再提供服务商与模型细节。近译不建设收费升级流程；预置演示不能替代真实可用的默认翻译。

默认服务若引入项目中转，将改变当前“无自有服务器、请求直达用户配置服务”的数据路径与运营成本，应明确显示实际处理方、费用规则和数据处理说明。此处是需要形成方案的产品依赖，本次没有开通服务或改变现有数据流。

错误路径也要形成闭环：目前 AUTH 和余额错误有中文说明，但卡片中的“打开设置”动作只对 CONFIG 提供。应让能通过设置修复的错误直接到相应配置，不要求用户自己找入口。[错误分类](../../src/core/errors.ts#L30)、[卡片错误操作](../../src/ui/translator/Translator.tsx#L212)

建议验收：10 名未使用过项目、没有 API Key 的普通测试者，在网络正常且默认服务可用的条件下，至少 8 名能在安装完成后 3 分钟内获得首个真实译文；若注册或授权流程导致失败，也计入首用失败。另测高级 BYOK 的连接诊断。以上是拟议验收目标，不是当前成绩。

**4.2 通用质量：验证日常内容、不同语言与真实连接**

目前提示词已强调否定、条件、数字、公式与代码标识符，适合继续深挖。但现有 15 个真实质量样例尚未全部执行；多服务 0.7.0 的协议验证是模拟响应，真实 API 未逐一验证。[提示词](../../src/core/prompts.ts#L5)、[质量样例](../development/QUALITY_SAMPLES.md)、[0.7.0 验证](../development/VALIDATION.md)

建议发布服务能力矩阵，分别标注“真实连接已测”“模拟协议已测”“结构化词典/句法已测”。0.7.0 的 Chrome 浏览器回归尚未完成，后续发布前也应补齐；历史 Chrome 版本通过不能替代当前版本验证。[最新验证记录](../development/VALIDATION.md)

现有 15 例保留为历史基线，再建立通用语料集，覆盖新闻、购物说明、社交短句、工作邮件、帮助文档和技术内容；按首发支持的语言分别评估。可以从约 60 条样例起步，但不能用少量样例替所有语言背书。记录配置、原文、译文、关键约束、人工判断、首内容时间、完成时间和可获得的 token 用量。非英语样例需要相应语言的评审能力。句法分析单独评价；“成功解析 JSON”不能等价为“语法判断正确”。

与竞品做两组对照：一组尽量使用相同模型，观察页面提取、上下文和交互造成的差别；另一组按产品默认路径，观察普通用户的完整体验。仍然不同的提示词和参数要记录，不能把所有差异归于模型或扩展。

建议发布条件：固定样例中的数字、否定、条件和人名/产品名等关键错误完成复核和处理；技术子集继续检查代码和公式。公开覆盖范围与失败案例，不以“100% 准确”宣传。后续用普通用户的阅读和表达任务检验效果，不能仅统计请求成功率。

**4.3 稳定与成本：多服务以后，DeepSeek 的调度参数不应成为统一假设**

整页当前固定最多 32 个 worker；遇到 RATE_LIMIT 会停止会话，用户手动重试。这个策略有明确边界，并非没有错误处理，但它无法针对不同账号额度和本地推理速度自动调整。[并发常量](../../src/page/batches.ts#L2)、[限流处理](../../src/page/session.ts#L41)、[停止条件](../../src/page/session.ts#L213)

优先提供保守默认值与可配置上限，按服务保存设置；429 后降低并发、遵守可用的重试信息并采用有限退避，完成过的部分不重复发送。鉴权和配置错误应直接引导修复，不能无限自动重试。是否切换服务应由用户控制，因为它会改变文本接收方和计费来源。

provider 当前会跳过只有 usage 的 SSE 块，事件契约也没有用量事件，界面尚未形成成本反馈链路。[协议读取](../../src/providers/openai-compatible.ts#L203)、[事件契约](../../src/shared/contracts.ts#L33)

大众界面优先显示完成量、剩余额度、重试状态及是否需要付费；请求数、token 和并发配置可放进高级诊断。费用只在价格与用量可靠时估算，并明确标为估算；拿不到用量时显示未知。页面缓存先保留现有内存策略，持久化缓存以后作为可选项提供期限与清除入口。

**4.4 术语与上下文：保留为长文和专业用户的增强能力**

划词已有最多 600 字符上下文；整页批量分支提交的是各段文本，没有显式篇章标题、章节摘要或用户术语表。批次内部可能有相邻文本，但不等于稳定的全篇语境机制。长段还会按约 1,600 字符拆分，因此需要专门观察跨分块指代和术语一致性。[批量提示词](../../src/core/prompts.ts)、[分块策略](../../src/page/batches.ts#L6)

Read Frog 已提供按网站限定的术语表和保留原词选项，整页的 Smart Context 也明确说明额外调用、延迟和 token 成本。这些是可借鉴的产品边界，而不是简单加长上下文即可解决的问题。[术语表](https://www.readfrog.app/en/docs/glossary)、[页面上下文](https://www.readfrog.app/en/docs/page-translation)

这部分在大众路线中排在首用、多语言、网页适配和常见场景之后。进入该阶段时，可先提供个人术语与保留词，只注入命中项，并让纠正能保存到适用范围；再试验标题/章节上下文，比较收益和成本。`kernel`、`alignment`、`condition` 等多义词不能仅靠全局替换。若通用质量评测证明上下文缺失造成高频严重错误，对应修复应提前，不受功能排期限制。

缓存与重复文本复用也应考虑模型、目标语言、术语版本和有效上下文；当同一句话出现在不同语境时，不应默认结果总是可互换。这里是未来扩展的设计要求，不表示本次已证实发生误译。

**4.5 高频操作与站点适配：从“有按钮”到“每天省操作”**

工具栏弹窗目前主要提供说明、PDF 与设置入口，没有直接翻译当前网页的按钮；网页主按钮则已经支持翻译、停止和恢复。这会让从浏览器工具栏进入的用户多找一步。[弹窗](../../src/entrypoints/popup/main.tsx#L25)、[网页工具条](../../src/page/Bar.tsx#L23)

当前整页提取从 body 开始，已有隐藏/代码/输入区等排除，但没有用户级站点偏好和正文优先选择。翻译后的新文本是纯文本节点，原网页链接和强调保留，不代表译文中具有可点击链接和对应强调。前者是安全且稳妥的基础，后者仍是可改进的阅读体验。[提取入口](../../src/page/segments.ts#L59)、[译文渲染](../../src/page/render.ts)

建议将当前页快捷操作、正文优先、此站点禁用/始终翻译、悬浮栏隐藏和译文样式列入 P0，并提供双语/仅译文/原文切换。翻译范围与语言偏好需要可见、可撤销；复杂 CSS 规则编辑留给高级用户，普通用户先获得简单的站点设置与问题反馈入口。KISS 正式版已有规则订阅、快捷键与可视化选区修正规则，说明“遇到坏页面后怎么自救”已经是成熟能力。[正式版功能与规则编辑说明](https://github.com/fishjar/kiss-translator/blob/v2.1.1/README.md)

建议建立至少 20 个代表性页面的适配集，覆盖新闻、电商商品与评价、论坛、帮助文档、社交动态、工作网页和技术文档，并包含动态加载与表格。分别记录漏译、误译界面文本、布局破坏和重复请求，不能只看 API 成功率。

可访问性已经有键盘激活、Esc、标签与焦点样式，后续应补完整纯键盘流程、卡片打开/关闭的焦点去向、读屏结果通知和 200% 缩放验收，而不是把它当成从未建设过的能力。[语法标记](../../src/ui/translator/AnnotatedSentence.tsx#L18)、[网页按钮](../../src/page/Bar.tsx#L27)

**4.6 学习积累：增强功能，优先级低于通用翻译主流程**

在本次检索的 UI、契约和设置中，未发现词句收藏、复习、发音或学习导出链路。现有“不持久化原译文”是明确设计选择，增加学习功能需要用户主动保存和清晰的数据边界。[设置与结果契约](../../src/shared/contracts.ts#L10)、[隐私说明](../guides/PRIVACY.md)

建议后续以“收藏词/句 → 连同原句与来源保存 → 回看 → 导出”作为最小增量。生词本、间隔复习和深度句法不应阻挡大众用户直接得到译文。长难句拆解可以保留为按需展开或自愿开启的模式，普通翻译默认避免额外分析请求；朗读可作为独立便利功能评估，不必与完整学习系统绑定。

Read Frog 已将无账号翻译与需要账号的 Notebase/复习区分；Trancy 的阅读模式也将词句收藏放在内容消费过程中。这些可作为学习用户路径的参考；普通用户是否再次使用近译，还应通过网页覆盖、速度和易用性验证，不能假定复习功能会提升所有用户的留存。[Read Frog 方案边界](https://www.readfrog.app/en/docs/account-and-plans)、[Trancy 阅读模式](https://manual.trancy.org/en/get-started/use-extension/bilingual-subtitles/read-mode)

**4.7 PDF：先承认能力层级，再选择可控的增量**

近译的 PDF.js 阅读器已有翻页、搜索、缩放、密码与跨页选区，属于基础较好的文字 PDF 划词工具。但它没有形成整页双语、完整文档导出或扫描件 OCR 流程。阅读说明书、工作文件或论文时，逐段划选与文档直接翻译的操作成本不同。[README](../../README.md)、[PDF 验证](../development/VALIDATION.md)

沉浸式有文字 PDF 双语翻译与 PDF Pro 等分层方案；Trancy 的 PDF 路径包括文本提取、双语对照与截图问答。它们与近译当前的划词阅读器属于不同覆盖层级，不能在功能表里只用同一个“支持 PDF”勾选项。[沉浸式 PDF 文档](https://immersivetranslate.com/en/docs/features/pdf/)、[Trancy PDF](https://www.trancy.org/pdf)

大众路线将文字 PDF 的按页和全文翻译提前到 P1：先支持有进度、可停止/恢复的双语阅读，再增加下载/导出与复杂版式。扫描件 OCR、双栏、公式和版式重建分别验收，不以实现划词或简单文本导出就宣称完整 PDF 翻译能力。成熟竞品的文档方案本身也区分不同模式和限制。[沉浸式 PDF 文档](https://immersivetranslate.com/en/docs/features/pdf/)

**4.8 多语言与读写覆盖：通用定位的必要基础**

当前提示词和译文语言标签指向英译简中；已确认目标浏览器为桌面 Chrome/Edge。源/目标语言选择、输入框翻译、视频字幕、图片 OCR、移动平台及原生 Anthropic/Responses 协议，均不是当前已完成的通用能力。[提示词](../../src/core/prompts.ts#L6)、[渲染语言](../../src/page/render.ts#L25)、[支持范围](../../README.md)

多语言现在是 P0。先确定可实际验收的语言集合，例如中英双向与日/韩/法/德到中文作为候选，而不是先列出大量语言名称。自动检测应允许用户纠正，并明确“页面语言”和“目标语言”。现有页面识别依赖拉丁字母与汉字比例，提示词、词典判断和句法展示也偏向英文，因此不能只加一个语言下拉框就认为支持完成。[页面语言筛选](../../src/page/segments.ts#L22)

输入框翻译列为 P1，覆盖邮件、评论和聊天等表达任务；提供结果预览、明确替换和撤销，不自动发送用户消息。图片/截图翻译与已有字幕双语作为下一轮候选，根据普通用户的真实任务频率选择顺序；无字幕语音转写的成本和适配另算。跨平台在桌面核心流程稳定后逐步扩展。

原生协议接入继续由实际需求推动；当前 Chat Completions 兼容已覆盖多种服务，增加预设列表不能替代默认服务、多语言与场景覆盖。

**5. 已确认定位下的可交付路线**

建议验证的产品表述是：**“装好就能用的通用翻译助手，让网页、词句和常用文档更容易读懂，也方便用外语表达。”**

大众通用定位已确认，但上述价值主张是否能让用户切换仍需验证。优先比较安装后首次成功率、常见网站覆盖、操作次数、速度稳定性与费用可理解性。沉浸式也已有简洁模式，“简单”本身不是独家能力，需要用任务完成体验证明。[官方更新日志](https://immersivetranslate.com/zh-Hans/docs/CHANGELOG/) 开源、BYOK 和句法拆解保留为选择理由之一，不让它们增加普通用户的配置负担。

| 阶段 | 交付内容 | 进入下一阶段前的判断 |
| --- | --- | --- |
| A：大众网页翻译基础 | 明确默认服务与成本方案、商店安装与升级；无需 Key 的首用、多语言、当前页快捷入口、阅读模式、站点偏好；配套质量和稳定性验证 | 无 Key 的新用户能独立得到译文；已声明语言和代表页面通过验收；服务成本与额度可控 |
| B：读写与文档 | 输入框翻译、文字 PDF 按页/全文双语、进度与恢复；完善反馈和故障诊断 | 普通用户可连续完成读网页、查词、写回复、读文件；失败有明确恢复路径 |
| C：扩展内容形态 | 图片/截图 OCR 或已有字幕双语按需求排序；后续再做无字幕转写和复杂文档排版 | 实际任务收益高于成本与适配负担，不损害网页核心体验 |
| D：进阶与平台 | 术语/篇章增强、收藏与可选学习、多浏览器和移动平台 | 对应人群需求已验证；功能按需出现，普通模式保持简单 |

这些是交付顺序，不是未经估算的日历承诺。阶段 A 范围较大，应拆成可验收的小版本；默认服务决策与网页体验改进可并行，但无需 Key 的大众首用依赖真实可用的服务和成本方案。商店分发、安装包、升级说明与反馈入口属于大众发布基础，不再后置为可选项。

近译保持免费，不设计会员或收费能力。默认路径优先评估用户自己的官方授权权益和浏览器本地能力，显示上游实际用量边界；上游额度耗尽时暂停或由用户主动选择其他已配置服务，不自动购买或切换计费。BYOK 继续保留为可选项。

**6. 如果下一轮只能做三件事**

1. **真正降低首用门槛**：商店安装、无需自备 Key 的默认路径、清楚的额度与错误提示，BYOK 作为高级选项。
2. **补齐通用语言能力**：源语言识别、目标语言选择与偏好记忆，逐语言验证真实质量。
3. **打磨每天使用的网页翻译**：当前页快捷入口、双语/仅译文切换、站点偏好、动态网页适配与稳定恢复。

真实质量、限流恢复与成本测量贯穿这三项。下一批优先输入翻译和文字 PDF；术语库、收藏复习和长难句增强后置。

建议后续用小规模自愿测试收集首用成功率、整页完成率、严重误译、首段与全文 P50/P95 时间、请求/用量以及再次阅读行为。当前没有这些用户数据，不对活跃、留存、转化或市场份额作事实判断；也不需要为获得初期证据立即增加生产遥测。
